## 3. ✅ Fixed — `job-hunt email reconcile --apply` reversed human corrections

**Fixed and merged 2026-09-19.** Recorded here because the failure is worth remembering.

Before the fix it did not touch the two rejections it was run for, and instead moved:

- **#667 Lumerate** Applied → `Interview`
- **#669 Micro1** Responded → `Interview`

Both had been corrected on 2026-09-10 after reading the source mail. Lumerate's classifier
had matched the word "interview" inside *"…if we wish to schedule an interview"* — a plain
acknowledgement; no interview ever happened. Micro1 was an invitation to an automated
AI-recruiter screening that was never completed and whose deadline had passed.

The stored event keeps the bad classification, and the reconciler has no notion that a
human already overruled it. **Reverted.** This is the same mechanism that produced the
inflated statuses found in the 2026-07 review.

**The fix.** `EmailDecisionRepository.decided_event_ids()` already recorded exactly this
— an event a human has approved or ignored — and `list_review_candidates` has always
filtered on it. `reconcile` was the one caller that did not consult it. It does now, and
reports `Left alone, already ruled on by a human: N` so a run that skips something says
so. The two events were marked ignored with the reason, so the 2026-09-10 corrections are
now durable. Re-running the exact command that caused the regression leaves the tracker
byte-identical. Covered by two tests in `tests/test_email_reconcile.py` — one that the
guard holds, one that an undecided event still advances a row, so the guard cannot quietly
freeze reconcile.

**Workflow that follows from it:** when you overrule a classification, run
`job-hunt email ignore-event <event_id> --note '<why>'` as well as changing the row.
Changing the row alone is what was not sticking. There is still **no CLI for a status
change** — `job-hunt tracker` has `verify / merge / dedup / normalize / dashboard /
check-sync` and nothing else — so status edits go into `data/applications.md` by hand,
with the date and the evidence in the note.

## 4. ✅ Closed root cause — résumé experience ordering

Ten of the seventeen hand-written résumés listed dated roles by JD-relevance instead of
reverse-chronologically. Root cause, in three layers:

1. The rule existed in exactly one place — `profile/redteam-facts.md:430` — which is the
   **reviewer's** ground truth. Nothing the writer reads stated it.
2. `prompts/evaluate/tailor_cv.md` tells the writer to reorder by relevance four times and
   states the Experience exception once (line 52, "in the same order"). Hand-written
   résumés never pass through that file. The pipeline is unaffected: it inherits the order
   from `profile/cv.md`, which is correct.
3. The only gate was the LLM red team, and it *asserted* compliance without checking — the
   Manitoba r2 report says "Experience is reverse-chronological" about a résumé that was not.

The control was the page budget: same batch, same author, same review, **17/17 correct**,
because `render_cv.py --max-pages` deletes the PDF and exits non-zero.

**Fixed:** `check_experience_order()` in `scripts/render_cv.py` refuses to render before
the PDF exists (exit 1). Verified against all 17 run directories and the 15 CV variants
under `profile/` with no false positives. Covered by `tests/test_cv_experience_order.py`
(6 cases); full suite 1374 passing. `CLAUDE.md` gained §2b, stated where the writer reads.

`brampton`, `vancouver`, `quadbridge`, `university-of-alberta`, `yukon-hospitals`,
